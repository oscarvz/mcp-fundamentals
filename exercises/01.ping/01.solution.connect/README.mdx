<summary>🦉 What the StreamableHttpTransport does</summary>

The `StreamableHttpTransport` enables your MCP server to communicate over HTTP
using standard web APIs. Unlike stdio-based transports that spawn processes,
HTTP transport works like a regular web server.

The MCP Client connects to your server's HTTP endpoint (e.g., `http://localhost:3000`)
and sends JSON-RPC requests as POST requests.

### How HTTP Transport Works

When you start your server, it listens on a port (default 3000):

```ts
import { createServer } from 'node:http'

const httpServer = createServer(async (req, res) => {
	// Read request body
	const body = await getRequestBody(req)
	const url = `http://localhost:${PORT}${req.url}`

	// Convert Node.js request to Web API Request
	const request = new Request(url, {
		method: req.method,
		headers: req.headers as HeadersInit,
		body,
	})

	// Get response from MCP handler
	const response = await handler(request)

	// Send response back
	res.statusCode = response.status
	response.headers.forEach((value, key) => {
		res.setHeader(key, value)
	})
	res.end(await response.text())
})

httpServer.listen(3000)
```

### Example: Ping Request and Response

The client sends a `ping` request as an HTTP POST with a JSON-RPC body:

```bash
curl -X POST http://localhost:3000 \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":"123","method":"ping"}'
```

The server processes this and responds:

```json
{ "jsonrpc": "2.0", "id": "123", "result": {} }
```

### Key Differences from Stdio

**With Stdio (old approach):**

- Client spawns a child process
- Communication via stdin/stdout streams
- Process-specific, harder to test
- Can't work across networks

**With HTTP (current approach):**

- Client makes HTTP requests to a URL
- Standard Request/Response APIs
- Easy to test without spawning processes
- Works across networks
- More familiar to web developers

### Request/Response Cycle

1. **Client** sends POST request with JSON-RPC payload
2. **Node.js http server** receives the request
3. **Server code** converts Node.js IncomingMessage to Web API Request
4. **Handler** processes the request and returns a Response
5. **Server code** sends the Response back to the client

### StreamableHttpTransport Pattern

```ts
import { McpServer, StreamableHttpTransport } from 'mcp-lite'
import { zodToJsonSchema } from 'zod-to-json-schema'
import type { z } from 'zod'

const server = new McpServer({
	name: 'epicme',
	version: '1.0.0',
	schemaAdapter: (schema) => zodToJsonSchema(schema as z.ZodType),
})

const transport = new StreamableHttpTransport()
const handler = transport.bind(server)

// handler is now a function: (request: Request) => Promise<Response>
```

The `bind()` method connects the transport to your server and returns a
handler function that accepts standard Web API Request objects and returns
Response objects.

#### ⚠️ Note about logging

Just like with stdio, you should use `console.error` for logging instead of
`console.log`. While HTTP doesn't have the same stdout mixing issue as stdio,
using `console.error` is a good practice for server logs to separate
diagnostic output from response data.

#### Testing Benefits

HTTP transport makes testing much easier. You can test your server in-memory
without spawning processes:

```ts
// In your tests
const request = new Request('http://localhost/mcp', {
	method: 'POST',
	headers: { 'Content-Type': 'application/json' },
	body: JSON.stringify({
		jsonrpc: '2.0',
		id: '123',
		method: 'ping',
	}),
})

const response = await handler(request)
const body = await response.json()
// Assert on body
```

Other transport mechanisms exist as well, and while the code for them is
different the underlying concept is the same: a server and client
communicating with each other using a standard protocol.
